# vital_monitor 医疗器材合规与功能优化方向

> **文档目的**：以医疗器械（多参数监护仪上位机软件）的标准，系统梳理本项目在**功能、规范性、安全性、合规性**方面的可优化空间，作为后续迭代与改进的路线图。
>
> **免责声明**：本文基于 IEC 62304、IEC 60601-1-8、ISO 14971、IEC 62366-1、IEC 81001-5-1 等通用标准的**工程实践层面**进行评审，**不构成任何法规符合性认定，也不构成法律意见**。本项目当前定位为学习与技术演示 Demo（见 `README.md` 第十二节"仅用于学习与技术演示"），若要成为真实医疗器械，绝大部分差距属于**流程与质量体系**范畴，需依法规机构与专业团队完成。

## 一、评审结论概览

### 1.1 项目现状定性

| 维度 | 现状 | 医疗器械要求 | 差距等级 |
|------|------|------------|---------|
| 数据源 | 模拟器（`VitalSignSimulator`） | 真实传感器 + 信号质量监测 | 🔴 架构级 |
| 报警系统 | 单阈值 + 去抖 + 视觉三角标记 | IEC 60601-1-8 全谱要求 | 🔴 重大 |
| 事件日志 | UI 文本日志（内存，不落盘） | 审计追踪，不可篡改 | 🔴 重大 |
| 数据完整性 | 无校验、无时间戳同步保证 | 数据完整性与时钟同步 | 🟠 中等 |
| 风险管理 | 无 FMEA / 危害分析痕迹 | ISO 14971 强制 | 🔴 流程级 |
| 软件生命周期 | 无 SOUP 清单、无需求追溯 | IEC 62304 A/B/C 级 | 🔴 流程级 |
| 网络安全 | 无（CSV 明文导入导出） | IEC 81001-5-1 | 🟠 中等 |
| 可用性工程 | 未开展 | IEC 62366-1 | 🟠 中等 |

### 1.2 工程优点（应保持）

在指出差距之前，先明确本项目**已经做对、且符合专业工程实践**的部分：

- **四层解耦架构**：数据采集 / 业务数据 / 绘图 / UI 层次清晰，便于测试与替换。
- **线程模型正确**：采集对象 `moveToThread()`，仅通过 `QueuedConnection` 信号槽通信，采集线程绝不触碰 UI 对象；自定义类型已通过 `qRegisterMetaType` 注册。
- **内存可控**：`RingBuffer` 定长 + `QReadWriteLock` 保护，支持长时间运行，内存上限恒定。
- **绘制性能优化**：静态网格背景预渲染缓存 + 局部重绘 + 批量提交，交互时不扰动原始数据。
- **坐标映射分离**：`CoordinateMapper` 独立维护各通道 Y 轴量程，绘图不参与业务计算。

## 二、报警系统（最高优先级）

> 报警是监护仪**最核心的临床安全功能**，也是本项目差距最大、最应优先改进的部分。
> 相关代码：`src/core/AlarmDetector.cpp`、`src/data/SampleData.h`、`src/chart/TrendChartWidget.cpp`

### 2.1 现存问题清单

| # | 缺失能力 | 标准要求 | 当前实现的问题 |
|---|---------|---------|---------------|
| 1 | **报警优先级语义** | 高 / 中 / 低三级，且需与**技术报警**（导联脱落、传感器故障）区分 | 仅 `Info/Warning/Critical`，且严重度用"超出阈值半个量程"折算（`AlarmDetector.cpp:41-42`），**非临床定义**，医护无法据此决策 |
| 2 | **报警限随患者变化** | 生理报警限应可配置，并支持按患者类型（成人/小儿/新生儿）预设 | `alarmLow/alarmHigh` 为全局固定值，**无患者类型概念**（SpO₂ 阈值在新生儿与成人间差异巨大） |
| 3 | **技术报警** | 导联脱落、传感器断连、信号低灌注等必须报警 | **完全缺失**。真实场景下传感器脱落不报警可能致命 |
| 4 | **报警延时可控可验证** | 报警条件延时（alarm condition delay）需量化并可验证 | `m_debounceFrames = 3` 以**帧数**计，换算时间是浮动的（10 Hz → 300 ms），缺少最坏情况论证 |
| 5 | **静音 / 暂停 / 确认** | 必须具备无声、暂停功能，且有明确的**重新激活策略**与可视指示 | 无静音、无暂停、无确认机制 |
| 6 | **报警声光指示** | 听觉 + 视觉双通道，音量分级，颜色符合 IEC 60601-1-8 色码 | 仅有曲线上的三角标记，**无声音、无闪烁、无独立报警状态栏**（`README.md` 第 250 行甚至将其列为"可扩展方向"，但对监护仪这是**必需项**） |
| 7 | **报警状态机** | 未确认 / 已确认 / 已静音 / 暂停 / 超时升级 | 无状态机 |

### 2.2 ⚠️ 关键逻辑缺陷：告警"只报一次"

**位置**：`src/core/AlarmDetector.cpp` 第 31–54 行

```cpp
// ---- 上限判断 ----
if (cfg.hasHighAlarm && s.value > cfg.alarmHigh) {
    ++st.highCount;
    if (st.highCount >= m_debounceFrames && !st.highLatched) {  // 锁存后不再上报
        /* ... 生成一次 AlarmEvent ... */
        st.highLatched = true;
    }
} else {
    st.highCount = 0;
    st.highLatched = false;   // 只有回落到阈值内才解锁
}
```

**问题**：`highLatched` 一旦置位，**只有数值回落到阈值内才会解锁**。这意味着：

> 若患者心率持续 180 居高不下，**临床医护只会收到一次报警**，此后不再有任何提醒。

真实监护仪的报警必须是**持续性/周期性**的，直到被**确认（acknowledge）**或**报警条件解除**。这是本项目中最接近"临床危险"的一个点，建议优先修复。

### 2.3 改进建议（可落地）

**第一层（必须）**
1. **报警状态机**：`Idle → ConditionActive → Annunciating → Acknowledged → Silenced`
2. **持续提醒**：危重且未确认时，按间隔（如每 5 s）重复刷新报警状态，而非仅上报一次
3. **独立技术报警通道**：`TechnicalAlarm` 与 `PhysiologicalAlarm` 分离
4. **报警延时以毫秒计**，并纳入需求文档

**第二层（推荐）**
5. **患者类型预设**（成人 / 小儿 / 新生儿）+ 报警限剖面（Alarm Profile）
6. **报警声光指示**：分级提示音 + 报警条闪烁 + 状态栏常驻显示
7. **报警静音 / 暂停 / 确认**，配明确的可视倒计时与自动重新激活策略

## 三、信号采集与数据完整性

> 相关代码：`src/data/VitalSignSimulator.cpp`、`src/core/RingBuffer.h`、`src/core/ChannelConfig.h`、`src/core/HistoryRecorder.cpp`

### 3.1 现存问题

| # | 问题 | 说明 |
|---|------|------|
| 1 | **无信号质量指示（SQI）** | 真实监护仪必须显示信号质量（SpO₂ 低灌注、ECG 噪声），并对低质量数据**抑制报警或标记**，以防误报 |
| 2 | **时间戳可信性不足** | `SampleFrame.timestampMs` 用 `QDateTime`，无单调时钟保证；回放使用 `50 ms` 定时器重放（`MainWindow::onPlaybackTick`），时间轴与原始时间戳脱钩 |
| 3 | **无数据丢失检测** | `RingBuffer` 只保证容量，不检测丢帧、乱序、重复帧 |
| 4 | **无生理合理性校验** | 缺少范围校验、变化率校验（如 HR 单帧从 60 跳到 200 应判定为伪迹） |
| 5 | **`clamp()` 用于数据路径有风险** | `ChannelConfig::clamp()` 直接裁剪到量程。若被用于告警判断路径，会把真实异常值（如 HR 250）裁成量程上限，**掩盖病情**。经核查，`AlarmDetector::detect` 当前使用原始值 `s.value`（正确），但需在文档与代码注释中**明确禁止**将 clamp 结果送入告警判断 |

### 3.2 改进建议

1. **信号质量指标（SQI）**：为每个通道增加质量评分，低质量数据在曲线上以虚线/灰色呈现，并抑制其生理报警
2. **时间戳规范**：采用单调时钟（`QElapsedTimer`）+ 可选系统时间校准；保证每个数据点可回答"何时测得"
3. **数据完整性**：丢帧 / 乱序 / 重复检测与上报；为存档文件增加校验（如每行 CRC 或整文件哈希）
4. **生理合理性校验层**：范围 + 变化率双重校验，异常值标记为伪迹而非静默裁剪
5. **采样抖动补偿**：`VitalSignSimulator` 使用 `Qt::PreciseTimer`（正确），但仍需对长时间运行的累积漂移做补偿，避免 `sampleIndex` 与时间戳分离

## 四、审计追踪与事件持久化

> 相关代码：`src/ui/MainWindow.cpp`（`appendLog`）、`src/core/HistoryRecorder.cpp`、`src/data/SampleData.h`（`AlarmEvent`）

### 4.1 现存问题

- 日志仅进入 UI 控件（内存），**程序退出即全部丢失**
- **无配置变更记录**：`ChannelConfigPanel` 修改量程 / 阈值 / 报警限**没有任何审计痕迹**
- **告警事件未持久化**：`AlarmEvent` 仅存在于 `m_alarmBuffer` 与 UI，无落盘
- 无用户身份、无操作者标识、无设备标识绑定

### 4.2 改进建议

1. **审计追踪（Audit Trail）模块**：记录「谁 / 何时 / 改了什么配置 / 旧值 → 新值」，尤其是报警限修改
2. **告警事件持久化**：`AlarmEvent`（含确认记录）写入文件，格式可复用现有 CSV 风格
3. **不可篡改存储**：采用追加写入、写保护或哈希链（每条记录含前一条哈希）
4. **统一时间戳格式**：审计与告警日志使用 ISO 8601 带时区的时间
5. **复用现有能力**：项目已有 `HistoryRecorder` 的落盘能力，在其上扩展审计模块**工程量小、合规价值高**

## 六、可用性与人因工程

> 参考标准：IEC 62366-1（医疗器械可用性工程）

### 6.1 现存问题

| # | 问题 | 说明 |
|---|------|------|
| 1 | **报警色码未严格合规** | 曲线三角标记使用 `#E74C3C` / `#F39C12`（`TrendChartWidget.cpp:392-394`），接近但未严格对照 IEC 60601-1-8 色码规范 |
| 2 | **无报警声音** | 听觉报警通道完全缺失 |
| 3 | **参数修改无二次确认** | `ChannelConfigPanel` 修改报警限无确认、无日志——临床误改报警限是**已知重大风险源** |
| 4 | **多通道读数难以分辨** | Y 轴刻度仅显示首个可见通道（`TrendChartWidget::drawYAxis` 第 287–301 行 `break;`），多通道混叠时无法分辨数值 |
| 5 | **无抗误操作设计** | 缺少操作锁定、关键参数只读、修改确认等机制 |
| 6 | **可用性测试缺失** | 未做医护人员参与的可用性测试 |

### 6.2 改进建议

1. 严格按 IEC 60601-1-8 定义报警色码、图标与优先级视觉表现
2. 增加**分级听觉报警**（高/中/低不同声型与音量）
3. 关键参数（报警限、量程）修改增加**二次确认 + 审计记录**
4. **每通道独立 Y 轴刻度**（左右两侧分列），提升多通道可读性
5. 开展**可用性工程流程**：使用场景分析、任务分析、形成性/总结性评价
6. 提供**演示模式 / 临床模式**区分（本项目数据的模拟性质应显著标识，避免误导）

## 七、可靠性与健壮性

> 相关代码：`src/core/RingBuffer.h`、`src/ui/MainWindow.cpp`、`src/data/VitalSignSimulator.cpp`

### 7.1 现存问题与改进点

| # | 问题 | 说明与建议 |
|---|------|-----------|
| 1 | **历史数据不持久化** | `RingBuffer` 容量固定（`60000` 帧 / `2000` 告警）→ 内存恒定（优点），但断电即全丢；旧数据被静默淘汰且无提示。建议：定时增量落盘 + 淘汰提示 |
| 2 | **文件损坏无容错** | `HistoryRecorder::loadFrames` 失败仅弹 `QMessageBox`，无损坏文件容错或部分恢复。建议：按行容错解析，跳过坏行并上报 |
| 3 | **时间精度漂移** | 采样周期抖动累积未补偿。建议：漂移补偿与周期性时间戳校正 |
| 4 | **配置快照线程安全待确认** | `MainWindow::onFrameReady`（主线程）与 `requestUpdateConfigs` 之间共享 `m_configMgr.channels()` 快照，需确认无竞态；建议显式加锁或使用不可变快照 |
| 5 | **无开机自检（POST）** | 医疗器械通常需开机自检并显示结果。建议：启动时校验缓存、文件系统、配置完整性，并给出明确结果 |
| 6 | **无看门狗 / 心跳监控** | 长时间运行建议增加采集线程心跳检测，异常时自动恢复并记录 |
| 7 | **异常处理不完整** | 建议对文件 IO、内存分配、线程启动失败建立统一错误处理与用户提示机制 |

## 八、网络安全

> 参考标准：IEC 81001-5-1（健康软件网络安全）

### 8.1 现存问题

- CSV 文件**明文导入导出**，无完整性校验，可被篡改
- 无用户身份认证与权限控制（任何人可修改报警限）
- 无 SBOM（软件物料清单）、无漏洞管理流程
- 无传输加密（如未来接入 HIS / 中央站时）

### 8.2 改进建议

1. 导出文件增加**数字签名或哈希校验**，导入时验证
2. 引入**用户身份与权限模型**（查看 / 配置 / 管理分级），关键操作需授权
3. 建立 **SBOM** 与第三方依赖漏洞扫描流程
4. 预留**加密通信**能力（对接中央监护站 / 医院信息系统时）
5. 对导入文件做**输入校验**（防路径穿越、超大文件、畸形数据）

## 十、优化优先级路线图

### 第一梯队（改动小、价值高，建议立即做）

| 序号 | 任务 | 涉及文件 | 价值 |
|-----|------|---------|------|

## 附：一句话总结

> 本项目的**工程架构（四层解耦、线程安全、环形缓冲、QPainter 自绘）干净且专业**，作为上位机 Demo 质量较高。但从医疗器械角度看，最大的短板不在架构，而在三处：
>
> 1. **报警系统**不满足 IEC 60601-1-8（无声音、无技术报警，且存在"只报一次"的潜在临床风险）；
> 2. **审计追踪与事件持久化**缺失；
> 3. **缺少软件生命周期与风险管理的过程文件**（决定它能否被称为"医疗器械"）。
